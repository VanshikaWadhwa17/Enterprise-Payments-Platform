# Deployment runbook

This covers taking the Enterprise Payments Platform from `docker-compose` on a
laptop to a real cloud deployment: **backend on Railway, frontend on Vercel.**
It assumes you've already read the code changes in this phase (runtime
frontend config via `env.js`, configurable cookie `Secure`/`SameSite`,
env-driven CORS) — this document is about what to click and set, not what the
code does.

**Everything in this document is performed by you, in your own accounts.**
Nothing here was run as part of writing it — no account was created, no
payment method was used, and nothing was deployed.

## 1. Platform decision: Railway (backend) + Vercel (frontend)

**Backend — Railway:**

| Criterion | Railway | Render |
|---|---|---|
| Price (this workload) | Usage-based (~$20/vCPU-mo, $10/GB RAM-mo, metered by the second) | Flat per-instance (~$7–25/mo each); 7 services + Postgres + Redis + a Kafka private service adds up fast |
| Docker support | Any Docker image, first-class | Docker supported, but private services/background workers are a distinct product tier |
| Postgres / Redis | Native managed add-ons | Native managed add-ons |
| Kafka | No managed product, but official ready-made KRaft-mode templates with private networking already worked out | No managed product, no equivalent template |
| Private networking | Free, built-in (`RAILWAY_PRIVATE_DOMAIN`) | Free, built-in, same-region requirement |
| Env vars | Per-service **and project-level shared variables** — one place to set `AUTH_JWT_SECRET` for all 4 services that need it | Per-service only |
| Deployment simplicity | Point each service at `backend/<service>/` — matches this repo's existing per-service Dockerfile layout | Same Dockerfile-per-directory model works |

**Railway is the selected platform because its project-level shared variables and ready-made Kafka template fit this specific architecture** — not a claim that it's universally the better platform. **Re-verify current Railway pricing and template availability before you deploy** — these are external details that can change after this document was written.

**Frontend — Vercel:** the 4 deployable Angular apps (shell/payments/fraud/reconciliation) build to static SPA bundles — Vercel is a purpose-built static/Jamstack host for exactly that shape of artifact (git-integrated builds, per-project preview deployments, a CDN, and a generous free tier), rather than running each app as its own nginx container the way `infra/angular.Dockerfile` does for Docker/Railway hosting. **The `env.js` runtime-config mechanism from this phase is what makes the split possible without any application code changes** — the same `window.__env` contract works whether `env.js` gets generated by `infra/40-generate-env-js.sh` at container start (Docker/Railway) or by `scripts/generate-env-js.mjs` at build time (Vercel, which has no persistent container to hook a startup script into). `infra/angular.Dockerfile` and the Docker-based frontend path are left fully intact — they still work for local `docker-compose` and remain a fallback if you ever want to self-host the frontend on Railway instead.

## 2. Before you start

- A Railway account and a Vercel account (create these yourself — see the note above).
- This repo pushed to a GitHub repo both Railway and Vercel can access.
- Decide your domain topology now — it changes which cookie config you use in step 5. With frontend on Vercel and backend on Railway, **the two are on entirely different platform domains by default** (`*.vercel.app` vs `*.up.railway.app`) — both are on the Public Suffix List, so this is always cross-site unless you map custom domains for both onto the same apex domain:
  - **Custom domain** (recommended): you own a domain and point `app.yourdomain.com` (Vercel) and `api.yourdomain.com` (Railway) at it.
  - **Default platform domains**: no custom domain, using `*.vercel.app` and `*.up.railway.app` directly.

## 3. Create the Railway project and backend services

For each of the 7 backend services, create a new Railway service pointed at the corresponding subdirectory:

| Service | Directory | Needs |
|---|---|---|
| payment-service | `backend/payment-service` | Postgres, Redis, Kafka, `AUTH_JWT_SECRET` |
| auth-service | `backend/auth-service` | Postgres, `AUTH_JWT_SECRET` |
| account-service | `backend/account-service` | Postgres, Redis |
| fraud-service | `backend/fraud-service` | Postgres, Kafka, `AUTH_JWT_SECRET` |
| notification-service | `backend/notification-service` | Kafka |
| audit-service | `backend/audit-service` | Postgres, Kafka |
| reconciliation-service | `backend/reconciliation-service` | Postgres, `AUTH_JWT_SECRET` |

Railway auto-detects the `Dockerfile` in each directory — no build config needed beyond pointing the service at the right path.

Add:
- **Postgres**: one Railway Postgres add-on, one database per service (matches today's single-instance/multiple-databases setup) — or one Postgres add-on per service if you prefer full isolation.
- **Redis**: one Railway Redis add-on, shared by payment-service and account-service.
- **Kafka**: deploy from Railway's KRaft-mode Kafka template (single broker is enough for this workload). Every consumer/producer service points its `KAFKA_BROKERS` at the Kafka service's `${{Kafka.RAILWAY_PRIVATE_DOMAIN}}:9092`.

## 4. Environment variables (backend)

Set `AUTH_JWT_SECRET` **once**, as a Railway **project-level shared variable**, and reference it (`${{shared.AUTH_JWT_SECRET}}`) from auth-service, fraud-service, payment-service, and reconciliation-service — these four must all receive the byte-for-byte same value, and it must be 32–47 bytes for HS256 (see `JwtService`'s fail-fast check). **Generate a fresh value — do not reuse the one in your local `.env`:**

```bash
openssl rand -base64 32
```

Per service (values reference Railway's own generated variables for Postgres/Redis/Kafka — check each add-on's "Variables" tab for the exact names it exposes):

| Variable | Value |
|---|---|
| `DB_HOST` / `DB_PORT` / `DB_NAME` / `DB_USER` / `DB_PASSWORD` | From the Postgres add-on's connection variables |
| `REDIS_HOST` / `REDIS_PORT` | From the Redis add-on's connection variables |
| `KAFKA_BROKERS` | `${{Kafka.RAILWAY_PRIVATE_DOMAIN}}:9092` |
| `CORS_ALLOWED_ORIGINS` | The deployed frontend origin(s), comma-separated (e.g. `https://app.yourdomain.com` or `https://epp-shell.vercel.app`) |
| `AUTH_JWT_SECRET` | `${{shared.AUTH_JWT_SECRET}}` (auth/fraud/payment/reconciliation only) |
| `COOKIE_SECURE` | `true` |
| `COOKIE_SAME_SITE` | See the table in step 5 — depends on your domain topology |

## 5. Cookie configuration — pick based on your domain topology

This is a hard gate, not a "set it and forget it" value — the correct config depends entirely on whether your frontend and backend end up on the same registrable domain. With frontend on Vercel and backend on Railway, **this is always cross-site by default** — `vercel.app` and `up.railway.app` are both on the Public Suffix List, so two different apps under either one are treated as different sites regardless of platform.

| Topology | `COOKIE_SECURE` | `COOKIE_SAME_SITE` | Notes |
|---|---|---|---|
| Local (unchanged) | `false` | `Lax` | Default in every `application.properties` — no action needed |
| **Custom domain** (recommended) — e.g. `app.yourdomain.com` (Vercel) + `api.yourdomain.com` (Railway) | `true` | `Lax` | Same registrable domain — cookies work cleanly, no known browser limitations |
| **Default platform domains** — `*.vercel.app` + `*.up.railway.app` | `true` | `None` | Required for the cookie to be sent cross-site at all — **Safari and private-browsing windows will still block it as a third-party cookie regardless of this setting.** This is a known platform limitation, not something the app can fix in code. |

Given the frontend/backend split is on two different vendor platforms, a custom domain is the more reliable path here, not just a nice-to-have — both Vercel and Railway support adding one with a simple CNAME/A record.

## 6. Deploy the frontend to Vercel

Create **4 separate Vercel projects** — one each for shell, payments, fraud, reconciliation — all pointed at the same GitHub repo. Vercel needs the whole Nx workspace present to resolve shared `libs/*`, so for every project:

- **Root Directory**: repo root (leave as `.` — do not point it at `apps/<app>`)
- **Install Command**: `pnpm install --frozen-lockfile`
- **Build Command** (differs per project — this is what makes each project build a different app):
  ```
  node scripts/generate-env-js.mjs <app-name> && npx nx build <app-name> --configuration=production
  ```
  e.g. `node scripts/generate-env-js.mjs shell && npx nx build shell --configuration=production` for the shell project.
- **Output Directory**: `dist/apps/<app-name>/browser` (e.g. `dist/apps/shell/browser`)

`vercel.json` at the repo root is shared by all 4 projects — it adds the wildcard `Access-Control-Allow-Origin` header Native Federation needs to fetch `remoteEntry.json`/chunks cross-origin between these 4 separate Vercel deployments (the same thing `infra/nginx/spa.conf`'s CORS header does for the Docker path), and rewrites unmatched paths to `index.html` for Angular's router — existing static files (JS chunks, `remoteEntry.json`, `env.js`) are still served directly, this only catches paths that don't correspond to a real file.

Set these environment variables per Vercel project (in the project's dashboard, **not** committed anywhere) — **these are public URLs only, never secrets**, since `env.js` ships to every browser that loads the app:

| Variable | Used by | Value |
|---|---|---|
| `GRAPHQL_PAYMENTS_URL` | shell, payments | `https://<payment-service>.up.railway.app/graphql` |
| `GRAPHQL_FRAUD_URL` | shell, fraud | `https://<fraud-service>.up.railway.app/graphql` |
| `GRAPHQL_RECONCILIATION_URL` | shell, reconciliation | `https://<reconciliation-service>.up.railway.app/graphql` |
| `AUTH_API_URL` | shell | `https://<auth-service>.up.railway.app` |
| `REMOTE_PAYMENTS_URL` | shell | `https://<payments-project>.vercel.app/remoteEntry.json` |
| `REMOTE_FRAUD_URL` | shell | `https://<fraud-project>.vercel.app/remoteEntry.json` |
| `REMOTE_RECONCILIATION_URL` | shell | `https://<reconciliation-project>.vercel.app/remoteEntry.json` |
| `REMOTE_REPORTS_URL` | shell | (leave pointing at a placeholder until Reports is deployed — it's not containerized/deployed yet) |
| `REMOTE_ADMIN_URL` | shell | (same caveat as Reports) |

`scripts/generate-env-js.mjs` regenerates `apps/<app>/public/env.js` from these at build time, before `nx build` copies `public/` into the output directory — the same `window.__env` contract works whether it's Vercel (build-time) or Railway/Docker (container-start via `infra/40-generate-env-js.sh`) generating it.

## 7. Production readiness gate

Phase C isn't done when the code compiles or Railway says deployed — walk this checklist against the actual deployed environment before calling it done:

- [ ] All backend Dockerfiles have correct `EXPOSE` ports
- [ ] The frontend's `env.js` contract works identically whether generated at container start (local/Railway/Docker) or at build time (Vercel) — no application code differs between them
- [ ] No production secrets are committed anywhere in the repo
- [ ] Production `AUTH_JWT_SECRET` is freshly generated — not copied from the local `.env`
- [ ] Postgres reachable from every service that needs it
- [ ] Redis reachable from payment-service and account-service
- [ ] Kafka reachable from payment/fraud/notification/audit services
- [ ] `CORS_ALLOWED_ORIGINS` on every backend service contains the actual deployed frontend origin(s)
- [ ] HTTPS active on every public service
- [ ] `epp_token` cookie has the expected `Secure`/`SameSite` for the chosen topology (step 5)
- [ ] `XSRF-TOKEN` cookie has matching `Secure`/`SameSite`
- [ ] Login works against the deployed URL in a real browser
- [ ] `/me` (session restore) works after a hard page refresh
- [ ] Logout works
- [ ] Protected GraphQL requests succeed (payment/fraud/reconciliation)
- [ ] RBAC still behaves correctly (spot-check at least one restricted role)
- [ ] Payment → Kafka → Fraud/Audit/Notification event flow still works end-to-end
- [ ] Frontend MFEs load their remote bundles (Native Federation works across deployed origins)
- [ ] **No `localhost` URLs remain in the deployed frontend's browser bundle** — open browser devtools, check the Network tab or `view-source:` on the deployed `env.js`; it should show your real deployed URLs, not `localhost`
- [ ] Railway logs show no startup/configuration errors on any backend service
- [ ] Vercel build logs show no errors on any of the 4 frontend projects, and each one's deployed `env.js` reflects that project's own env vars (not another app's, and not the dev defaults)
